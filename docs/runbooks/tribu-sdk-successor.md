# Receiver-compatible Matrix updates

## Routine maintenance path

Use this path for an already authorized ordinary software update. The detailed
sections below explain existing mechanisms and recovery cases; they are not a
sequence of additional gates to repeat for every iteration.

1. Resolve the current selected generation and the consumers affected by the
   actual change. Preserve the existing body, keys, native history and goals.
   A routine update is not onboarding, a species release or a new authority act.
2. Prepare one candidate from that verified current selection with
   `onboarding_code_successor.build(..., current=..., current_fingerprint=...)`.
   Reuse the qualified SDK artifact directly; the builder already copies it
   into the candidate, so an extra input/staging copy is unnecessary locally.
   Cold SDK installation and closed-import preparation use the same remaining
   declared finite maintenance envelope (at most480seconds overall), before any
   service stop. Each SDK/migration call remains capped at300seconds. Cold
   installation must not silently reduce a480second request to300seconds total.
   Ordinary observation and physical controls retain their60second limit. A
   preparation timeout leaves the serving selection intact; inspect its retained
   installation/import receipts before continuing the same operation.
   When both daemon behavior and the installed foundation client change, include
   `onboarding_runtime.py`, `onboarding_foundation_native.py` and
   `onboarding_owner_client.py` in this same candidate. The owner-client capture
   already includes its pinned `onboarding_chat_native.py`; do not list that
   companion again. Separate client and daemon builds are unnecessary.
3. Prepare the SDK/imports once using the existing helpers. Reuse unchanged
   qualification and receiving evidence; run the checks that resolve the changed
   behavior and the repository's actual required checks. One coherent scenario
   can establish several outcomes without a report or fixture for every label.
4. Select through the existing scoped maintenance and native configuration writer.
   If the foundation client changed, point its existing MCP role at the same
   qualified candidate using `foundation_command` and `register_codex_mcp`.
   Reuse the retained operation and expected prior command. Keep chat and
   unrelated native configuration intact. An SDK-only server fix does not need
   client reconfiguration when that client remains compatible and unchanged.
5. Observe the changed receiving behavior and, when affected, the existing native
   catalog/current context. Retain the result in the same update checkpoint.
   On uncertainty inspect that operation instead of rebuilding or replaying it.
   Retire consumed duplicate transfer/input files after verifying the retained
   copy; preserve active selections, actual rollback and unfinished work.

Run maintenance with the existing qualified Cluster environment, which includes
its Matrix SDK. After a timeout, inspect the same operation's retained publication
before recovery. An already exchanged exact publication can be acknowledged after
its original admission deadline without another grant, counter advance or expiry
extension. Continue that same specification; never restore an earlier counter.
If the native update completed and only reader completion failed, reuse its
retained update receipt with the existing reader completer. Its expired-selection
recovery preserves old commands and qualifies the current CAS and credentials;
another software deployment or capability expansion is unnecessary.

If an owner read refuses `qualified_runtime_imports_required`, inspect its actual
closed-import verification failure before changing a service. Extra generated
`__pycache__/*.pyc` files can invalidate an otherwise unchanged selected SDK.
Keep observer/diagnostic launches on the existing `runtime_command` (`-B`, isolated
imports and its disabled-bytecode prefix); do not import the selected tree through
an ordinary interpreter. For a confirmed cache-only repair, retain the offending
file hashes, verify every expected file against the exact selected wheels, and
retire only unexpected generated bytecode under the existing SDK lock as its
owner. Requalify the same owner read. Missing/modified wheel files or other extras
are not this case and must not be deleted to make validation pass. This adds no
automatic cleanup, relaxed verifier or service restart. The10November Root repair
retired108extra bytecode files after verifying all1147wheel files; the producer
was not identified and is not inferred from their timestamps.

Routine scoped delivery already within the human's task needs no repeated GO,
new identity ceremony, mandatory multi-reviewer quorum or unrelated full-stack
rehearsal. Confirm a substantial service-loss risk and honor explicit global Stop,
custody and host restrictions. Resource limits and stop controls bound ongoing
work; finite acceptance-run counters and expiry are not species or deployment
prerequisites for ordinary updates.

## Canonical TCP authority restart

Scoped authority maintenance must retain the original signer, configuration and
store and stop only its selected Matrix clients. The TCP listener permits
same-address reuse after close, while an existing live listener still excludes
another authority (no SO_REUSEPORT). This avoids a TIME_WAIT-only EADDRINUSE gap;
it does not permit parallel authorities or weaken signed admission/fences. The
first transition from an older listener without address reuse may still need its
existing TCP connections to expire. Inspect actual closed startup diagnostics
and exact listener state; do not stop an unrelated VPN proxy or recreate custody.
